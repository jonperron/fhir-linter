### main red, 2026-11-17

Dependabot #137 (pest_derive) and #142 (pest) each added
`pest_stack_guard`, `shlex` and `stacker` to `Cargo.lock`. Git merged
both without a conflict and kept both copies, so every build failed
with "package specified twice". #128 was then merged on that red CI by
a `wait && merge` chain whose wait script exited 0 whatever the result. The fix, #143, removed the duplicates (checked with `cargo metadata --locked`).

### Not fixed

Date vs zoned DateTime comparison, `hasValue()` on a Coding, days on
year / month precision values, href validity, conditional references,
fhirpath-bad / null and Bundle-local `resolve()`, blocks in inline
elements other than `p`. Not this round (M-L): decimal precision, UCUM,
`type()`, static type checking, StructureDefinition instance
validation, tx-server cases.

Open question for the maintainer: only the CLI caps input size (64 MiB);
the parser, the bindings' `validate()` and direct library calls have
only the depth cap of 128. Should the library enforce a byte cap?

## Lessons and the changes they led to

| What happened | Change |
|---|---|
| #128 was merged on red CI: the wait script exited 0 and printed `fail,pass`, and the merge was chained after it | `loop.md`, After the push: the poll script exits non-zero on a failed or cancelled check (step 1); merge only as a separate, gated command (step 6) |
| Two Dependabot PRs touching `Cargo.lock` merged cleanly and broke `main` | `project.md`: `cargo metadata --locked` in the quality gate; merge `Cargo.lock` PRs one at a time on CI with current `main` |
| Reviewer handbacks never reached a driver (#129); the orchestrator reran them | `loop.md`, Reports: `verdict missing` instead of "passed" |
| Responders ran only `rust-reviewer` or none after code changes and did not re-measure the manifest (#128, #145) | `loop.md`, Reports and `bot-review-responder` step 4: every routed agent with its verdict or `not run: <reason>`; "the gate covered it" is not a verdict; re-measure the manifest after code fixes |
| A responder declined a Sourcery CRITICAL without evidence; the orchestrator disproved it in code (#127) | `loop.md`, After the push, step 3, and `bot-review-responder` judgement guide: verify first, decline with code evidence, a confirmed one goes to the maintainer |
| Validator items could not run in parallel: they all edit the same spec file | `project.md`, Spec sync: a spec file is a serialisation point |
| One final PR raised the floors (#146); no conflicts on the constants. The validator spec also states them and was stale | `project.md`, Spec sync: shared floors, spec included, go in one final PR |
| The auto-mode classifier was unavailable: Bash, Edit and ScheduleWakeup failed with "no verdict" | `project.md`, Shell quirks: stop and report, do not spend the attempt limit |

Not changed. These are orchestrator practice and do not belong in an
agent file:

- About 7 agents at once hit the 5-hour usage limit; two died mid-task
  and resumed after the reset with SendMessage. Keep about 4 at once;
  use Sonnet for responders and read-only work.
- Drivers still overran the budget (111k, 130k, 186k): the checkpoint
  works only when the orchestrator sends a wrap-up message.
- Read-only design agents (Plan type) cannot write files: give them a
  writable path or take the plan from the message.
- Worktrees with submodules need `--force` to remove; finished ones
  pile up under `.claude/worktrees/`.
- `gh pr update-branch` worked for finished PRs whose owner had stopped.
- The repository moved to `jonperron/fhir-linter`; pushes work through
  the redirect, and the profile already uses the new name.
